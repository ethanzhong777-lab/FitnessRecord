## 1. 必须遵守的执行规则

1. 严格按阶段编号从小到大执行，不跳阶段。
2. 每个阶段必须完成“交付物”和“退出条件”后才能进入下一阶段。
3. 未完成当前阶段时，新想法记录到待办池，不直接插入开发。
4. 先确认需求和交互，再编写业务代码。
5. 每个功能都要覆盖正常、空数据、错误和边界状态。
6. 每次修改后至少运行 `npm run check` 和 `npm test`。
7. `main` 分支始终保持可运行；功能开发使用独立分支。
8. 每个阶段结束时更新本文档的状态表，并创建一个可回退的 Git 提交。
9. 不把 AppID、上传私钥、API Key、个人健康数据或其他秘密提交到 Git。
10. 不直接复制 openGym 的代码、图标、文案或动作媒体，只参考产品结构和交互。
11. 未核实许可证的动作图片、GIF、字体和图标不得进入正式项目。
12. 训练建议只能作为一般健身参考，不进行疾病诊断或伤病治疗指导。

## 2. 项目目标与第一版边界

### 2.1 产品目标

做一个轻量、私密、每天愿意使用的小程序，帮助用户：

- 持续记录每日体重；
- 直观看懂体重变化趋势；
- 制订并执行每周减脂增肌计划；
- 查阅动作步骤、目标肌群和安全提示；
- 根据自身条件获得可解释的训练建议。

### 2.2 MVP 必须包含

- 今日体重记录、补录、修改和删除；
- 目标体重设置；
- 7 天、30 天、3 个月和全部时间折线图；
- 动作搜索、部位筛选、动作详情和收藏；
- 自定义训练组合；
- 周一至周日训练安排；
- 基于目标、经验、训练天数、时长和器械的规则推荐；
- 本地数据导出、导入和清空；
- 首次使用、空数据、异常数据和风险提示。

### 2.3 MVP 明确不做

- 摄像头姿态识别、自动计数和实时纠错；
- 社区、好友、排行榜和分享裂变；
- 饮食图片识别和热量数据库；
- 广告、会员、支付和商业后台；
- 多用户管理和教练管理；
- 未经用户确认自动修改训练计划；
- 医疗诊断、康复治疗或替代专业意见的功能。

上述内容只能进入 MVP 完成后的候选版本，不能提前开发。

## 5. 阶段 1：开发环境与最小运行验证

### 目标

证明当前电脑能够完整执行“编辑代码 → 微信开发者工具编译 → 模拟器显示 → 真机预览”的基本链路。

### 输入

- 阶段 0 的项目骨架；
- macOS、Node.js、npm 和 Git；
- 微信账号和后续可选的小程序 AppID。

### 执行顺序

1. 安装微信开发者工具 macOS 稳定版。
2. 登录微信开发者工具。
3. 导入项目根目录，不导入 `miniprogram/` 子目录。
4. 首次使用测试号编译。
5. 确认模拟器显示“开发环境已就绪”。
6. 检查控制台无错误和持续警告。
7. 使用预览功能在一台真实手机打开。
8. 记录开发者工具版本和实际基础库版本。
9. 将 `project.config.json` 的 `libVersion` 从 `trial` 改为已验证版本。
10. 重新运行自动检查和测试。

### 交付物

- 首次编译结果；
- 一次真机预览记录；
- 更新后的 `docs/ENVIRONMENT.md`；
- 固定的基础库版本；
- 阶段完成提交。

### 退出条件

- 模拟器和真机都能打开占位页；
- 控制台没有阻断性错误；
- `npm run check` 与 `npm test` 通过；
- 环境版本已经记录并提交。

### 当前阻塞项

尚未安装微信开发者工具，因此本阶段不能标记完成，也不能进入阶段 2。

## 6. 阶段 2：需求确认与范围冻结

### 目标

把“想做什么”转换成明确、可测试、不会反复变化的需求。

### 执行顺序

1. 确认小程序正式名称和一句话定位。
2. 确认体重单位、目标体重、记录频率和补录规则。
3. 确认每周计划的训练类型、组数、次数、负重和休息字段。
4. 确认训练推荐所需输入项。
5. 确认动作指导内容深度与素材形式。
6. 确认导出、导入和清空数据的规则。
7. 把每项需求改写成“前提—操作—结果”的验收场景。
8. 对 MVP 内和 MVP 外项目进行最终确认。
9. 建立产品待办池，并按必须、应该、可以三个等级排序。
10. 冻结 MVP 范围。

### 交付物

- 更新后的 `docs/PRD.md`；
- 页面清单；
- 用户故事与验收场景；
- MVP 待办池；
- 范围冻结记录。

### 退出条件

- 每个 MVP 功能都有明确输入、输出和异常规则；
- 不存在“以后再看”“大概这样”等无法验收的描述；
- 用户确认需求范围；
- 冻结后新增需求只进入待办池。

## 7. 阶段 3：信息架构与交互原型

### 目标

在写业务代码前，验证页面结构和操作路径是否简单、完整。

### 执行顺序

1. 确认底部导航数量和名称。
2. 绘制页面地图和页面之间的跳转关系。
3. 绘制首页、趋势、动作库、计划和设置的低保真原型。
4. 补充首次使用、空数据、加载、错误和危险操作状态。
5. 串联五条核心路径：
   - 首次设置目标；
   - 记录今日体重；
   - 查看体重趋势；
   - 创建并安排训练；
   - 查找动作指导。
6. 使用示例数据完成可点击原型。
7. 按真实手机尺寸检查单手操作和信息密度。
8. 用户逐页确认。

### 交付物

- 页面地图；
- 低保真原型；
- 核心流程图；
- 页面状态清单；
- 原型验收记录。

### 退出条件

- 所有核心任务都能从首页开始并顺利完成；
- 危险操作都有确认或撤销机制；
- 页面层级不超过约定深度；
- 原型经用户确认后冻结。

## 8. 阶段 4：视觉规范与组件设计

### 目标

建立类似 openGym 气质、但拥有原创实现和适合中文阅读的视觉系统。

### 执行顺序

1. 确认深色主题、绿色强调色和品牌名称。
2. 定义颜色变量，包括背景、卡片、主色、文字、警告和危险色。
3. 定义字号、字重、行高、间距、圆角、阴影和触控尺寸。
4. 设计按钮、输入框、卡片、标签、弹窗、空状态和提示组件。
5. 设计折线图、周计划和动作卡片的专用规范。
6. 绘制高保真核心页面。
7. 检查中文换行、长文本、较大字号和安全区。
8. 建立素材来源与许可证登记表。
9. 用户确认视觉稿。

### 交付物

- 设计变量表；
- 通用组件规格；
- 核心页面高保真稿；
- 图标和素材清单；
- 素材许可证登记表。

### 退出条件

- 页面视觉已确认；
- 所有颜色和尺寸可以转成统一变量；
- 没有来源不明的素材；
- 开发无需自行猜测关键视觉规则。

## 11. 阶段 7：体重记录模块

### 目标

可靠完成每日体重的新增、补录、修改、删除和目标设置。

### 执行顺序

1. 实现 WeightRecord 模型和校验。
2. 实现体重 repository 和 service。
3. 实现首页体重摘要与快速记录入口。
4. 实现日期、体重和备注表单。
5. 实现同日覆盖确认。
6. 实现历史记录列表。
7. 实现编辑和删除确认。
8. 实现空数据、非法值和存储异常状态。
9. 编写服务测试和页面验收用例。
10. 在模拟器和真机完成主流程测试。

### 重点边界

- 拒绝非数字、负数、零和不合理范围；
- 内部统一使用 kg，显示时根据设置转换；
- 日期使用本地自然日，不使用 UTC 日期直接截取；
- 删除和覆盖必须二次确认；
- 用户取消操作不得改变原数据。

### 退出条件

- 所有增删改查场景通过；
- 重启小程序后数据仍正确；
- 体重单位转换不丢失精度；
- 自动测试和真机验收通过。

## 12. 阶段 8：体重趋势模块

### 目标

10. 完成视觉对照和真机测试。

### 退出条件

- 图表数值与原始数据一致；
- 90 天数据滚动和切换流畅；
- 单点与空数据不崩溃；
- 目标线和单位显示正确；
- 自动测试和真机验收通过。

## 15. 阶段 11：训练推荐模块

### 目标

根据用户条件生成一份可解释、可修改、必须确认后才能使用的训练建议。

### 推荐输入

- 目标：减脂、增肌或兼顾；
- 训练经验；
- 每周训练天数；
- 每次训练时长；
- 可用器械；
- 不希望安排的动作；
- 用户主动填写的限制或不适信息。

### 执行顺序

1. 定义规则优先级和冲突处理。
2. 建立每周 2、3、4、5 天的基础模板。
3. 根据器械和经验过滤动作。
4. 生成训练量、休息日和动作顺序。
5. 展示“为什么这样推荐”的解释。
6. 增加逐项修改、重新生成和放弃功能。
7. 用户确认后才写入周计划。
8. 对所有输入组合执行参数化测试。
9. 增加安全提示和异常兜底模板。
10. 完成用户验收。

### AI 使用规则

MVP 默认采用确定性的规则引擎。只有规则版本稳定后才评估 AI；AI 不得直接写入数据，必须生成变更建议并由用户逐项确认。

### 退出条件

- 所有支持的输入组合都有结果或明确提示；
- 相同输入能产生稳定、可解释的推荐；
- 推荐不会引用不存在的动作；
- 未确认时不修改用户计划；
- 自动测试和真机验收通过。

## 16. 阶段 12：设置与数据管理

### 目标

让用户能够管理目标、单位和自己的全部数据，并具备可靠恢复能力。

### 执行顺序

1. 实现目标体重和重量单位设置。
2. 实现主题与其他必要偏好设置。
3. 设计带版本号的 JSON 导出格式。
4. 实现导入前校验和导入预览。
5. 实现导入失败时不修改现有数据。
6. 实现清空数据的强确认流程。
7. 实现示例数据开启与重置。
8. 测试旧版本数据迁移。
9. 编写数据恢复演练记录。
10. 完成真机验收。

### 退出条件

- 导出后可在全新环境完整恢复；
- 无效文件不能破坏已有数据；
- 清空数据必须明确确认；
- 设置修改能正确影响相关页面；
- 自动测试和真机验收通过。

## 17. 阶段 13：集成测试与真机验收

### 目标

验证完整产品，而不是只验证单个页面。

### 测试范围

#### 功能测试

- 首次使用到完成第一条体重记录；
- 连续记录和修改体重；
- 趋势范围切换；
- 查找并收藏动作；
- 创建训练并安排到周计划；
- 生成、修改、确认和放弃推荐；
- 导出、清空和恢复数据。

#### 边界测试

- 无记录、单条记录和 90 天以上记录；
- 极小和极大合法值；
- 重复日期；
- 被删除动作的历史引用；
- 无存储空间或读写失败；
- 导入缺字段、错误版本和损坏文件。

#### 兼容性测试

- 微信开发者工具；
- 至少一台 iOS 或 Android 真机；
- 不同屏幕高度与安全区；
- 较大系统字体；
- 冷启动、后台恢复和离线状态。

#### 非功能测试

- 首屏可用速度；
- 图表渲染性能；
- 包体积与分包；
- 内存占用；
- 可读性和触控区域；
- 数据隐私；
- 素材许可证完整性。

### 缺陷等级

| 等级 | 定义 | 发布要求 |
| --- | --- | --- |
| P0 | 数据丢失、无法启动、严重隐私问题 | 必须修复 |
| P1 | 核心流程无法完成或结果错误 | 必须修复 |
| P2 | 非核心功能异常或明显体验问题 | 原则上修复 |
| P3 | 轻微视觉或文案问题 | 可进入后续版本 |

### 退出条件

- P0、P1 缺陷为 0；
- P2 已修复或有明确延期记录；
- 全部 MVP 验收场景通过；
- 数据恢复演练通过；
- 用户完成最终验收。

## 18. 阶段 14：发布与维护

### 发布前顺序

1. 冻结发布范围。
2. 更新版本号和变更记录。
3. 再次运行全部自动检查和测试。
4. 执行发布候选版真机验收。
5. 备份当前用户数据。
6. 核对 AppID、类目、隐私说明和素材许可证。
7. 创建发布提交和版本标签。
8. 上传体验版并完成最终检查。
9. 经用户确认后再提交审核或正式发布。
10. 保留上一版本和回滚说明。

### 维护流程

- Bug：复现 → 定级 → 测试用例 → 修复 → 回归 → 发布。
- 小功能：进入待办池 → 排期 → 按功能循环开发。
- 数据结构变化：先写迁移和测试，再修改页面。
- 依赖升级：核对更新内容、兼容性和许可证后单独提交。
- 每个正式版本都要更新 `CHANGELOG.md`。

### 退出条件

- 版本可安装、可运行、可回滚；
- 发布记录和变更记录完整；
- 用户数据已有备份；
- 没有未说明的高风险问题。

## 19. 每个功能都必须执行的小循环

无论处于哪个业务阶段，每个功能都按以下顺序完成：

1. **任务定义**：写清目标、范围和不做什么。
2. **验收场景**：先写可验证结果。
3. **交互确认**：确定页面、状态和操作反馈。
4. **技术拆分**：明确模型、服务、组件和页面修改。
5. **测试先行**：优先编写纯函数和数据层测试。
6. **最小实现**：只实现当前范围。
7. **自检**：运行 `npm run check` 和 `npm test`。
8. **界面检查**：检查正常、空、错误和边界状态。
9. **真机检查**：至少完成当前功能的主路径。
10. **文档同步**：更新需求、架构或说明。
11. **Git 检查**：确认没有秘密、临时文件和无关修改。
12. **提交与验收**：创建清晰提交，验收后才关闭任务。

## 20. Git 与版本管理规范

### 分支

- `main`：始终可运行。
- `feature/<name>`：新功能，例如 `feature/weight-log`。
- `fix/<name>`：缺陷修复。
- `chore/<name>`：工程、文档或依赖维护。

### 提交格式

```text
feat: add weight record form
fix: handle duplicate weight date
test: cover weight range validation
docs: finalize MVP acceptance criteria
chore: pin miniprogram base library
```

一次提交只解决一个明确问题。禁止把无关格式化、功能和素材混在同一提交。

### 提交前检查

```bash
git status
git diff --check
npm run check
npm test
```

### 版本约定

- `0.x.y`：MVP 开发和试用阶段；
- `1.0.0`：核心功能、数据恢复和真机验收全部通过；
- 补丁版本修 Bug，次版本增加向后兼容功能，主版本允许重大变化。

## 21. 质量门禁

任何阶段或功能只有同时满足以下条件才能标记完成：

- 需求与实际行为一致；
- 正常、空、错误、边界状态完整；
- 新增核心逻辑有自动测试；
- 所有检查和测试通过；
- 微信开发者工具无阻断错误；
- 真机主路径通过；
- 数据不会因失败操作被部分覆盖；
- 无秘密或个人数据进入 Git；
- 素材和依赖许可证已核实；
- 文档与代码同步；
- 用户完成阶段验收。

任何一项不满足，状态保持“进行中”或“受阻”。

## 22. 数据、隐私与安全红线

- 体重、训练记录默认只保存在本机。
- 未经明确确认，不上传、不分享、不同步个人数据。
- 导出和导入必须由用户主动触发。
- 删除、覆盖和清空必须确认。
- 导入失败必须保持原数据不变。
- 任何未来的云同步都必须先补充隐私说明、权限说明和安全设计。
- 不记录无关身份信息，不申请非必要微信权限。
- 日志不得包含完整个人健康数据或秘密。

## 23. 健身内容与建议红线

- 明确说明建议不是医疗意见。
- 出现胸痛、眩晕、异常呼吸困难或明显疼痛时，提示停止训练并寻求专业帮助。
- 不根据伤病描述给出诊断或康复处方。
- 推荐计划必须说明依据，并允许用户修改或拒绝。
- 初学者计划优先动作质量、恢复和渐进增加，不追求极端训练量。
- 不使用绝对承诺，例如“保证减重”或“必然增肌”。

## 24. 需求变更流程

阶段冻结后出现新想法时：

1. 写入待办池，不立即开发。
2. 标记提出原因、价值、影响页面和数据结构。
3. 判断属于当前 MVP、后续版本还是明确不做。
4. 评估对已完成阶段的返工范围。
5. 用户确认是否变更范围。
6. 如批准，先更新本文档和 PRD，再修改代码。
7. 单独提交变更记录。

紧急 Bug 可以中断功能开发，但必须先记录复现步骤和严重等级。

## 25. 阶段验收记录模板

- 真机验证：通过 / 未通过 / 不适用

## 26. 每次继续开发前的检查清单

后续每次开始工作前，都先回答以下问题：

1. 当前处于哪个阶段？
2. 当前阶段的退出条件是什么？
3. 本次任务是否属于当前阶段？
4. 是否存在未提交或来源不明的修改？
5. 是否需要先更新需求或设计？
6. 完成后要运行哪些测试？
7. 是否涉及个人数据、危险操作、外部服务或素材授权？

若本次任务不属于当前阶段，默认不执行，先进入待办池。
